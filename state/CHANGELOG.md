### research: evaluate CJK spacing normalization strategy (branch: research/case-003-mic-preregistration)

- **Layer-justified implementation, not an assumed fix.** Before touching code, explicitly compared 4 candidate architectural placements for the recurring pdfjs-baseline CJK-spacing artifact (extraction/reconstruction, engine-specific normalization, document/layout-family interpretation, semantic-matching tolerance) against evidence, and chose engine-specific normalization: PyMuPDF never exhibits the artifact, Docling already has its own independent instance of the identical rule (`closeCjkWrapSpaces`), and classifying it as "document-family interpretation" would contradict ADR-010's own definition of that layer (engine-independent rules), since the artifact is demonstrably engine-specific.
- Pre-change evidence traced the artifact to its source: pdfjs-dist's line-reconstruction heuristic inserts a space wherever the underlying glyph advance is wide, which happens consistently for `組織`/`項`-level header/total rows in this document family (both "List Creator"-produced) but not for ordinary body/expense-row text — confirmed by comparing spaced vs. unspaced rows *within the same raw artifact*, with case-001 (whose target page never contains such a header row) as a control showing zero artifacts, not derived from Ground Truth.
- Moved `closeCjkWrapSpaces` from `normalize-docling.mjs` to `common.mjs` as the shared canonical implementation (Docling re-exports it unchanged, verified byte-identical behavior); applied it in `normalize.mjs`'s `reconstructRow` for both flat-line engines.
- Pre-registered the expected impact before re-running: case-002 and case-003's pdfjs-baseline should gain `item_name_present_among_candidates`; case-001, PyMuPDF, and Docling should be untouched; no other check should move. **Every prediction matched exactly**: case-002 pdfjs-baseline 3/11→4/11, case-003 pdfjs-baseline 9/11→10/11, all else byte-identical (verified via normalized-JSON diff, timestamps excluded).
- 8 new tests added before the re-run (positive/negative cases: CJK↔CJK closes, CJK↔Latin and CJK↔digit preserved, fullwidth-punctuation-adjacency behavior made explicit, idempotence, re-export identity, and an end-to-end pipeline test through the real extraction regex with synthetic numbers). Full suite: 34/34.
- **Disclosed, not silently absorbed: a genuine collateral finding.** Fullwidth punctuation shares the closable Unicode range, so a space adjacent to it can also be closed; this materialized in case-001 and case-002 inside a value that was *already* wrong for an unrelated, pre-existing, explicitly out-of-scope reason (the annotation-column-contaminated `expenseNameFragment` from the known `splitTrailingTriple`/same-line-annotation issue) — zero PASS/FAIL outcomes were affected, since the field was FAIL before and remains FAIL after, just with one fewer space inside an already-garbled string. Recorded as a real, evidence-based architectural caveat (flat multi-column lines carry more legitimate-space risk than Docling's already-column-isolated cells) for future case work, not treated as grounds to withhold the fix, which produced zero observed harm and two genuine improvements across three real cases.
- No ADR added — this applies an already-established architectural pattern (ADR-010's engine-specific-normalization layer), not a new decision.
- Full report: `reports/document-understanding/20260926_1816_CJK_Spacing_Strategy_Layer_Experiment.md`.

### fix: harden docbench child-process reliability (branch: research/case-003-mic-preregistration)

- **Root-caused the case-003 `docbench` harness-reliability finding.** Not a Docling/Torch/child-process problem as first suspected in the case-003 first-run report — no subprocess, spawn, timeout, or resource-contention mechanism is involved at all.
- Root cause: `normalize-docling.mjs` had a standalone-execution convenience block at **module scope** (`if (caseIdArg) { normalizeDocling(caseIdArg); ... }`, reading `process.argv[2]`). Since `run.mjs` (which statically imports this module) is itself invoked as `node src/run.mjs <caseId>`, it shares the identical `process.argv[2]` — so merely `import`-ing the module re-ran `normalizeDocling()` **at import time**, before any adapter had produced a raw artifact, throwing `ENOENT` whenever `docling.raw.json` did not already exist on disk for that case. This was masked for `case-002` throughout the session because its stale raw artifact from earlier work was never deleted; `case-003`'s was repeatedly deleted while deliberately testing from a clean slate, which is exactly what exposed it. Confirmed with a single-line, zero-subprocess reproduction: `node -e "process.argv=['node','x','case-003']; import('./normalize-docling.mjs')"` throws the identical error on demand. `normalize.mjs` has the structurally identical pattern (latent, not currently triggered, since it requires two argv positions that `run.mjs`'s own single-argument invocation never supplies).
- Fixed by guarding both blocks with the same "only run on direct execution, never as an import side effect" pattern already established in this repository (`scripts/source-acquisition/browser-fetch/src/browser-fetch.mjs`, `scripts/source-acquisition/src/acquire.mjs`, both guarded identically after the earlier acquisition-immutability work).
- Verified no benchmark semantics changed: 5/5 clean-slate `npm run docbench -- case-003` runs succeeded post-fix; `case-001` (8/11, 8/11, 9/11), `case-002` (3/11, 4/11, 3/11), and `case-003` (9/11, 10/11, 3/11) all reproduce their historical scores byte-identically (modulo timestamps).
- Added 2 regression tests targeting the actual confirmed mechanism (spawning a fresh `node` process with a `run.mjs`-shaped `argv` and asserting the import does not throw for a nonexistent case), not the full Docling pipeline. Full suite: 28/28 passing.
- No ADR added — this is a bug fix already covered by existing engineering-quality expectations, not a new methodological/architectural decision.
- Full investigation, including the diagnostic path that led from an initially-wrong "Docling/child-process" hypothesis to the actual module-import-time cause: `reports/document-understanding/20260926_1737_Docbench_Harness_Reliability_Investigation.md`.
- Files: `scripts/document-understanding/benchmark/src/normalize-docling.mjs`, `scripts/document-understanding/benchmark/src/normalize.mjs`, `scripts/document-understanding/benchmark/src/test.mjs`, the investigation report, `state/{CURRENT_STATE.json,TODO.md,CHANGELOG.md}`.

### fix: enforce immutable source locks for HTTP acquisition (branch: research/case-003-mic-preregistration)

- **Source-acquisition infrastructure only. No case-003 row selection, no Ground Truth, no benchmark engine run.**
- The case-003 MIC source survey's own report flagged that `scripts/source-acquisition/src/acquire.mjs` still had the pre-PR-#2-review defect `browser-fetch.mjs` no longer has. Confirmed by direct code inspection, not assumption: `lockCommand()` wrote the canonical raw file unconditionally for every manifest source on every run (`fs.writeFileSync(rawFilePath(...), acquired.buffer)`, before any lock lookup), then unconditionally replaced or appended the lock entry (`lock.sources[existingIndex] = record`), with no validation beyond a bare `httpStatus` 2xx-range check — the same class of gap that let a WAF/bot-challenge page masquerade as a successful acquisition for METI, just never triggered here because the two manifest sources (Digital Agency) don't sit behind a challenge.
- Extracted the immutable lock-decision/mutation policy (`decideLockAction`/`applyAcquisition`, previously defined only inside `browser-fetch.mjs`) into a new shared, acquisition-method-independent module: `scripts/source-acquisition/src/lock-policy.mjs`. `browser-fetch.mjs` now imports and re-exports from it (identical behavior, verified via its own unchanged 7-test suite); `acquire.mjs` now uses it too, via a new `acquireAndLock()` wrapper that does status validation → PDF-magic-byte validation → `applyAcquisition()`, in that order, so a lock/raw write can only happen after the existing-lock comparison, never before it.
- New invariant, identical for both acquisition methods: new `sourceId` → writes raw + lock; existing `sourceId` + identical SHA-256 → succeeds as a no-op (`VERIFIED`/no lock or raw mutation, no `fetchedAt` refresh); existing `sourceId` + different SHA-256 → throws (non-zero exit) naming the `sourceId` and both SHA-256 values, without writing anything.
- Added PDF-magic-byte validation to `acquire.mjs`'s `lock` command (previously absent there; `verify`/`fetch` were already safe because their raw-file write is already gated behind a SHA-256 match).
- Added 8 new regression tests (`scripts/source-acquisition/src/test.mjs`): new source, identical re-fetch (lock byte-for-byte unchanged), mismatched re-fetch (lock and existing raw file both byte-for-byte unchanged, error names both hashes), non-PDF/WAF-style content rejected before any write, non-2xx status rejected before any lock lookup, and a direct check that the re-exported `decideLockAction` behaves identically to `browser-fetch`'s copy. All use fixture/temp directories and an injected `download` function — no live network request.
- Verified before and after: all 4 existing locked sources' SHA-256 in both `sources/source-lock.json` and `sources/raw/*.pdf` are byte-for-byte identical (case-001's 2 Digital Agency sources, METI case-002, and the MIC case-003 candidate locked in the prior task) — this fix did not alter any existing source identity.
- `npm run sources:verify` was run as a live smoke test (read-only; never writes the lock, and only materializes a raw file behind a SHA-256 match): 3/4 sources PASS; the pre-existing, already-documented METI WAF limitation (plain fetch cannot pass its bot challenge — Playwright/`browser-fetch` is the known workaround) reproduced as `FAIL` with no raw-file mutation, exactly as designed. This is a remote-availability fact, unrelated to and not masking the local SHA-256 identity checks above, which all passed via the deterministic unit tests.
- Documentation updated only where it had become false or misleading: `scripts/source-acquisition/README.md` (its "Source mutation" section previously implied re-running `sources:lock` was *the* way to update a lock to a new binary — now corrected to state that `lock` refuses a mismatched re-fetch) and `scripts/source-acquisition/browser-fetch/README.md` (its claim that "plain acquire.mjs" lacks magic-byte validation was no longer true; also noted the shared policy module). No new ADR: this brings `acquire.mjs` into compliance with the already-established ADR-009 policy, not a new methodological decision.

### PR #2 review fix: browser-fetch lock immutability (branch: research/case-002-meti-preregistration)

- **Fix only, scoped to `scripts/source-acquisition/browser-fetch/`. No case-003, no evaluator/Ground Truth/Case Package change, no PR merge.**
- Root cause: `browser-fetch.mjs` wrote the raw file and unconditionally replaced (`lock.sources[existingIndex] = record`) any existing lock entry for a re-fetched `sourceId`, contradicting the file's own header comment ("lock is explicit, reviewable, never silently overwritten") and ADR-009 — a same-`sourceId` re-fetch after an upstream PDF change would have silently replaced the old, reviewed lock entry with a new SHA-256, with no diff-worthy signal beyond the lock-file content itself.
- Fixed with a mutation-safe order: compute the new SHA-256 and compare it against any existing lock entry entirely in memory, *before* touching the raw file or lock file. Extracted this as two testable, exported functions in `browser-fetch.mjs`: `decideLockAction(lock, sourceId, newSha256)` (pure) and `applyAcquisition(...)` (performs the writes/throw). New behavior: identical SHA-256 → success, lock entry and raw file left completely unchanged (no timestamp refresh either); different SHA-256 → throws (non-zero exit), naming the `sourceId` and both SHA-256 values, lock entry and raw file left completely unchanged; unknown `sourceId` → writes raw + lock exactly as before.
- Added `scripts/source-acquisition/browser-fetch/src/test.mjs` (7 tests, fixture/temp-dir based, no browser/network dependency) covering: new source locks; identical-bytes re-fetch leaves the lock file byte-for-byte unchanged; mismatched-bytes re-fetch throws and leaves both the lock file and the existing canonical raw file byte-for-byte unchanged; the mismatch error message names the sourceId and both SHA-256 values. Added a `test` script to `browser-fetch/package.json`.
- Also fixed a latent side effect this refactor exposed: `browser-fetch.mjs` ran `main()` unconditionally at module-load time, so importing it from `test.mjs` for its exported functions also triggered a real (argument-less) CLI invocation. Guarded with a standard `require.main`-equivalent ESM check so `main()` only runs when the file is executed directly.
- README updated to describe the corrected immutability semantics (it previously said the tool "adds/updates the entry," which was the exact behavior being fixed).
- The already-recorded METI source lock entry itself is untouched by this fix — this only changes the tool's behavior on a *future* re-fetch of an existing `sourceId`.

### Evaluator overfit correction: delta_sign_evidence_matches_source (branch: research/case-002-meti-preregistration)

- **Methodology correction, not engine tuning.** The first frozen `case-002` run (`379043d`) exposed that `evaluate.mjs`'s `delta_glyph_observed_and_associated` check hardcoded `expected: 'contains △'` — a constant baked in from `case-001`'s source condition, not derived from Ground Truth. Since `case-002`'s frozen Ground Truth `deltaRaw` (`"4,556,824"`) correctly has no glyph, no engine could ever have passed this check on `case-002`, regardless of correctness.
- Replaced the check with `delta_sign_evidence_matches_source`, backed by a new exported, unit-tested pure function `deltaSignEvidenceMatches(expectedDeltaRaw, actualDeltaRaw)` in `evaluate.mjs`. The expected glyph state is derived from Ground Truth's own `deltaRaw` field (the most direct source-derived raw evidence), never from the sign of the normalized `delta`. Both directions are symmetric: PASS requires the engine's own `deltaRaw` to contain `△` when Ground Truth expects one, and to *not* contain a fabricated `△` when Ground Truth expects none. The existing provenance invariant is preserved: a `△` only counts as "observed" if it is genuinely present in the engine/normalizer's own output, never conjured from Ground Truth.
- Added 9 new unit tests covering both directions (glyph-expected, no-glyph-expected), the `null`/no-extraction case in each direction, fabricated-glyph rejection, and a symmetry check confirming no hardcoded bias. Full suite: 26/26 passing.
- **Re-evaluated both `case-001` and `case-002`** (evaluator-only change; adapters, normalizers, `run.mjs`, and both Ground Truth files verified byte-unchanged via `git diff --stat`; raw/normalized artifacts independently diffed before/after the rerun and confirmed identical modulo timestamps): `case-001` unchanged (8/11, 8/11, 9/11 — all three engines already had a genuine glyph); `case-002` up by exactly `+1` per engine (2→3, 3→4, 2→3), since no engine ever fabricated a false glyph — every other check's PASS/FAIL outcome was independently confirmed identical before and after for both cases.
