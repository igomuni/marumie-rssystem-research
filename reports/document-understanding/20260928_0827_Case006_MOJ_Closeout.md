## 6. Census classification → refined representation

The FY2024 format census's own provisional label for this authority was **"rasterized-no-text-layer"** — a label that served its purpose for candidate discovery (it correctly identified MOJ as a source with zero extractable text, a genuinely uncovered axis relative to case-001–005) but did not characterize the underlying *mechanism*. The Case-006 source survey **refined**, rather than falsified, this label: direct PDF object inspection (5 sampled pages) found zero font resources and, critically, **zero XObject/image resources anywhere** — meaning the source is not a scanned/photographed bitmap at all. Its visible content, including everything that reads as Japanese text, is drawn via **vector path-drawing operators** (filled Bézier curves and lines). This is recorded as a refinement of the census's own working vocabulary, not a correction of an error: the census-level observation ("zero extractable text") remains true and was the correct signal for selecting this authority; the source survey simply established *why*, at a level of mechanism the census's own broad sweep did not need to resolve for every authority. This refined mechanism is confirmed for the 5 pages object-inspected plus the 6 pages visually rendered in the source survey — it is **not** generalized to a claim that all 737 pages share the identical mechanism, per the source survey's own explicit disclosure.

## 13. Same-score/different-failure finding

The chain's own central, most important finding, restated precisely: **an identical aggregate score (2/11 for all three engines) conceals two fundamentally different failure situations.** For `pdfjs-baseline`/`pymupdf-baseline`, no usable textual signal is obtainable at all — the score reflects a pipeline-applicability boundary, not a document-understanding weakness. For `docling`, a meaningful character/numeric signal *was* obtained (via its own pre-existing OCR capability), but row/table structural association failed. **The existing 11 checks are not invalidated by this finding** — they correctly report FAIL for every content-accuracy check in both situations, exactly as designed. What this finding shows is that the *checks* measure task-level correctness at a single, fixed layer, and were never designed to also encode *why* a value is missing or *at which layer* recovery first became impossible — a genuinely different, currently-unaddressed axis that a future evaluator or Case Package design might need, not a defect in the current one.

## 14. Layered architecture implications

Using this program's own layer vocabulary (ADR-010, and the failure-layer language already used in the five-ministry synthesis), Case-006 demonstrates that a single source-representation finding does **not** imply a single, uniform failure layer across engines:

```text
pdfjs-baseline / pymupdf-baseline:
  source representation (vector-outline, no text objects)
    → text extraction boundary (FAILS HERE — nothing to extract)

docling:
  source representation (vector-outline, no text objects)
    → OCR-like recovery (SUCCEEDS SUBSTANTIALLY — most characters correctly recognized)
    → document/layout understanding (FAILS HERE — table-structure/grid association)
```

This is explicitly **not** generalized to "source representation problems always fail at the same layer" — Case-006's own evidence directly demonstrates the opposite: the *same* upstream source-representation fact produces failures at two different downstream layers, depending entirely on whether the specific engine has any fallback recovery mechanism at all.

## 15. Cross-case significance

Case-006's own novelty, stated at the evidence-bounded strength the originating task requires:

1. It is the first case in this program to hold the standard ledger grammar (unchanged from case-002–005) while varying only source *representation*.
2. Human-visible Ground Truth remained fully creatable by the same visual-transcription method as every prior case — representation did not block Ground Truth.
3. Flat-text engines (`pdfjs-baseline`, `pymupdf-baseline`) obtained zero signal, a genuinely new outcome relative to case-001–005 (all of which had at least some extractable text, however ambiguous).
4. Docling recovered substantial signal via its own pre-existing OCR capability — not by design of this research program, but as a pre-existing property of the compared toolchain, now empirically visible for the first time.
5. That recovered signal failed at table-structure association, not character recognition — a **third**, previously-unobserved Docling failure mode, distinct from case-002's row-under-pairing, case-003's row-over-merging, and case-004's column-fusion (none of which involved an OCR fallback at all).
6. An identical aggregate score across all three engines conceals this heterogeneity entirely — a direct, concrete illustration of why this program's own methodology insists on checking mechanism, not score, before drawing conclusions (the same discipline already established for the `item_name_exact_match` cross-case finding in the five-ministry synthesis).

`[FACT]` This is a single-case, single-selected-row observation. No general claim is made here about Docling's own OCR quality, about vector-outline PDFs generally, or about the rasterized census family as a whole (e.g., 金融庁/FSA has not been checked against this same mechanism).
