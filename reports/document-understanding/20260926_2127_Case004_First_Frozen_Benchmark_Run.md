## Per-engine raw → normalized → evaluated diagnosis

### pdfjs-baseline (7/11)

- **Raw** (`derived/document-understanding/case-004/pdfjs-baseline.raw.json`, reused from `scripts/pdf-extraction`'s deterministic line reconstruction, `page=2`): the target row is reconstructed cleanly as a single line, `lineIndex` 4: `"1 01-95 文部科学本省一般行政に 95,208,241 95,686,830 478,589"`, with its wrapped label continuation on `lineIndex` 5 (`"必要な経費"`). **No line on this page matches a genuine 3-digit item-code-header pattern for `010`** — the only 3-digit-prefixed lines present are `lineIndex` 6 (`"001 既 定 定 員 に 伴 う 経 費"`) and `lineIndex` 7 (`"001 人 件 費 90,317,220 ..."`), both subordinate sub-line-items nested *beneath* the target expense row, not the organization's own item header. No unit text (`(単位：...)`) appears anywhere in this page's lines.
- **Normalized**: `findItemCodeRows` correctly matches `ITEM_CODE_RE` (`^(\d{3})\s+(.+)$`) against both subordinate lines, producing two false-positive item-code candidates (`001`/`既定定員に伴う経費`, `001`/`人件費 90,317,220 90,331,254 14,034 令和５年度特別職 7人`). `findExpenseRows` correctly matches the target row exactly once. `unit` is `null` (no unit text found on this page, matching the Ground Truth evidence's own prediction).
- **Evaluated**: `item_name_exact_match` FAILs (two item-code candidates found, not one — `singleItem` resolution requires exactly one). `item_name_present_among_candidates` FAILs — **not because the correct row was garbled, but because it is not present on this page at all**; only the two false subordinate-line candidates exist. `expense_name_exact_match_after_line_join`, both amount checks, `signed_delta_exact_match`, `page_identification`, and `expense_to_amount_relationship` all PASS cleanly — the target row itself, and its own amount triple, were extracted and reconstructed correctly. `unit_exact_match` FAILs (raw `null` vs. expected `"千円"` — expected, per the Ground Truth evidence's own disclosure). `item_to_amount_relationship` FAILs: `precedingItemRow` resolves to `null`, because both false item-code candidates have a higher line-order than the target row (subordinate breakdown lines always come *after* their parent expense row in reading order), so neither satisfies the "preceding" ordering constraint even as a wrong candidate — the check finds nothing to associate, not a wrong association.
- **Earliest failure layer**: **document/layout-family interpretation** (ADR-010 taxonomy) — specifically, the current single-page-scope architecture (each case processes exactly `gt.pdfPageIndex`, with no cross-page context) cannot see the item header at all, because it is physically printed on a *different* page (`pdfPageIndex` 1) than the target expense row (`pdfPageIndex` 2). This is not an engine extraction defect: the engine's own page-2 extraction is accurate and complete for everything actually printed on that page.

### pymupdf-baseline (7/11)

- **Raw**: structurally identical finding to pdfjs-baseline — the target row appears as one reconstructed line (`"1      01-95 文部科学本省一般行政に                 95,208,241      95,686,830                                      478,589"`), and the same two subordinate-line 3-digit-prefixed lines are present, with no item header for `010` anywhere on the page. One genuine engine-specific difference from pdfjs-baseline: pymupdf's own line-reconstruction fused the `001 人件費` sub-line-item's entire staffing-count annotation block (`令和５年度特別職　7人`, etc.) onto the same physical line as the amount triple, producing a visibly longer, more fused false-candidate string than pdfjs-baseline's version of the same line (which kept the staffing annotation on the amount-triple's own line too, but pymupdf's own whitespace/column-gap heuristic produced wider inter-token spacing throughout).
- **Normalized/Evaluated**: identical check-by-check outcome to pdfjs-baseline, for the identical underlying reason (see above) — both flat-text engines see the same missing-item-header structural fact, independent of their own differing low-level line-reconstruction heuristics.
- **Earliest failure layer**: same as pdfjs-baseline — document/layout-family interpretation (single-page scope), not engine extraction.

### docling (5/11)

- **Raw** (`derived/document-understanding/case-004/docling.raw.json`, one table, 32 rows × 9 columns, 149 cells): the target row's own code+label cell is clean (`"01-95 文部科学本省一般行政に 必要な経費"`), but its own amount cells show a **new, genuinely different table-grid artifact from case-002/003**: three numeric-shaped cells appear to the right of the label in this row, in column order: (1) `"95,"` (a stray three-character fragment), (2) `"241 208, 830 686, 95,"` (a fused, reversed-token concatenation of *both* the previous-budget and current-request amounts' remaining digits), (3) `"589 478,"` (the delta, reversed-token, otherwise clean). No item-header row for `010` exists among Docling's own table cells either — the same two subordinate-line pseudo-item rows are present, plus a third false candidate discovered only in Docling's cell-level view: `"251 １既定分"` (table row 17, col 5) — a cell that fuses a subordinate line's own delta magnitude (`251`) with an unrelated annotation-column fragment (`１既定分`, "1, already-scheduled portion") from a *different* logical column that Docling's grid placed in the same cell. This passes the existing `looksLikeName` CJK-character safety guard (added specifically to filter reversed-numeric-token artifacts) because `既定分` is genuine CJK text — the guard does not, and was never designed to, distinguish a genuine item name from an amount-cell/annotation-cell fusion that happens to contain CJK characters.
- **Normalized**: `findTripleToTheRight` consumes the three numeric-shaped cells in column order — `previous` = `reconstructNumericToken("95,")` = `95`; `current` = `reconstructNumericToken("241 208, 830 686, 95,")` = reversed-token-joined `"95,686,830208,241"` → `95686830208241`; `delta` = `reconstructNumericToken("589 478,")` = `478589` (correctly positive, no glyph). `itemRows` ends up with 3 entries (`001`, `001`, and the new `251`/`１既定分`), none matching `010`.
- **Evaluated**: `previous_budget_exact_match` and `fy2024_request_exact_match` both FAIL (`95` and `95686830208241` vs. expected `95208241`/`95686830`) — a direct, traceable consequence of the column-fusion artifact above, not a random garble. `signed_delta_exact_match` still PASSes, because the delta's own cell happened not to be affected by the fusion. `item_name_present_among_candidates`, `item_to_amount_relationship` FAIL for the same underlying missing-item-header reason as the flat-text engines (plus the one additional false `251` candidate, which — like the other two — also has a higher row-order than the target expense row, so it likewise cannot satisfy the "preceding" ordering constraint). `expense_to_amount_relationship` PASSes (a triple, even if numerically wrong, was associated with the correct expense row) and `page_identification`/`delta_sign_evidence_matches_source` PASS.
- **Earliest failure layer**: **two distinct layers, not one** — (a) document/layout-family interpretation, identical missing-item-header cause as the flat-text engines, and (b) **engine extraction** (Docling's own table-cell segmentation), specifically a new column-fusion artifact where an apparently-empty visual column (visible in the source page's own render, between "6年度概算要求額" and "対前年度比較増△減") caused Docling's grid to split unevenly, stranding a fragment of the previous-budget cell into an extra cell rather than keeping both amount cells cleanly separated. This is genuinely different in *mechanism* from case-002's row-under-pairing and case-003's row-over-merging — here it is a **column**-level fusion within the *same* row, not a row-boundary error.

**Encryption compatibility is fully confirmed empirically for all three engines on this source; it played no role in any of the observed failures.** Every failure documented above is fully explained by document-layout/context-scope and table-grid mechanisms, not access restriction.

## Unit-context findings

Ground Truth evidence pre-registered that no unit label is printed on the target's own page (`pdfPageIndex` 2), and that `"千円"` was recorded with an honestly weaker, table-level (not page-level) scope, sourced from `pdfPageIndex` 0. The benchmark's current architecture confirms this exactly: `pdfjs-baseline`'s own `findUnitLabel` helper scans only the lines belonging to `gt.pdfPageIndex` (the single page each case is scoped to), found none, and correctly recorded `unit: null` — not a fabricated `"千円"`, and not a crash. `pymupdf-baseline` and `docling` show the equivalent `unit: None` / `unit: null` in their own raw output. This is not an engine-quality difference; it is an architectural consequence of the current single-page-scope design meeting a source where the relevant document-wide context genuinely lives on a different page than the one being evaluated — reported here as an observation, per the task's own instruction, not addressed with a fix in this task.

## Subordinate-breakdown findings

The deep numbered sub-line-item breakdown beneath the target row (flagged in the selection record and Ground Truth evidence) does measurably affect **candidate generation** for all three engines: every engine's `findItemCodeRows`/`findRows` genuinely matches the subordinate lines' own 3-digit prefixes (`001`, `001`, and Docling's additional `251`) against the same `ITEM_CODE_RE`/`ITEM_CODE_RE`-equivalent pattern used to detect genuine item headers, producing false item-code candidates. It does **not** affect row-boundary detection (the target expense row's own code/label/triple are correctly delimited in every engine) or the target's own amount association (`expense_to_amount_relationship` PASSes for all three). It **does** interact with Docling's grid geometry specifically: the `251`/`１既定分` false candidate is a genuinely new fusion of a subordinate line's own delta cell with an unrelated annotation-column fragment — a mechanism not previously observed, made possible by the sheer density of numbered sub-lines on this page giving Docling's grid many more opportunities for this kind of column misassignment than case-001/002/003's comparatively sparser target pages.

## Standalone-packaging findings

No observed failure in this run is attributable to MEXT's detail table being a standalone file rather than embedded in a combined document. The missing-item-header finding (the dominant new failure mode) is caused by **pagination distance** — the item header prints on the page immediately before the target expense row's own page — which is a document-layout fact independent of whether the file containing it is standalone or combined; case-002/003's combined files could in principle exhibit the identical pattern for some other row, and nothing about MEXT's standalone packaging structurally forces this outcome. This distinction is stated explicitly here because the task's own hypothesis (section D) invited investigating packaging as a candidate cause, and the evidence does not support attributing the pagination gap to packaging — the two are independent facts about this specific document.

**Similar (failure/success pattern already seen in another case):**

- `item_name_exact_match` FAILs for all three engines in every case observed so far, including case-004 — this check has never once passed across four independent cases, a now well-established, structural limitation (no case's target page has ever produced exactly one unambiguous item-code candidate).

**Different (same semantic target, different engine/layout mechanism):**
- Docling's `previous_budget_exact_match`/`fy2024_request_exact_match` FAIL for a **new mechanism**: column-level fusion of two adjacent amount cells via an apparently-empty visual column, distinct from case-002's row-under-pairing (wrong row silently selected) and case-003's row-over-merging (three rows collapsed into one cell).
- Docling's failure here is, like case-003's and unlike case-002's, traceable and honestly diagnosable — the garbled numbers are directly explainable from the raw cell content, not a silently-wrong-but-plausible-looking value.

**New (a failure/success mode not previously observed):**
- **`item_name_present_among_candidates` FAILs for all three engines**, including both flat-text engines (which passed this check in all of case-001/002/003). This is the headline new finding: in every prior case, the item header was present on the target's own page, and the check's failures came from hierarchy *ambiguity* (multiple candidates, one of which was correct). In case-004, the genuine item header is **entirely absent** from the target's own page — a categorically different failure (total absence vs. ambiguous presence), caused by the current architecture's single-page scope meeting a document where the item header and its first expense row are pagination-separated.
- **`item_to_amount_relationship` FAILs for all three engines** (previously PASSed for the flat-text engines in case-001/003, and FAILed only for Docling in case-002/003) — a direct consequence of the same missing-item-header finding, not a new independent defect.
- Docling's new column-fusion artifact (`251`/`１既定分`, and the previous/current amount-cell fusion) — not previously observed in case-001/002/003's own Docling failures.
- The deep subordinate-breakdown-driven false-candidate generation, while structurally similar in kind to case-003's own single extra intermediate level, is here dense enough to produce a third false candidate specifically through cross-column cell fusion (Docling only) — a new degree of consequence, not merely a new instance of an old pattern.

## Layer diagnosis (ADR-010 taxonomy)

- **Source/acquisition**: no findings — the source is correctly locked, unencrypted-for-reading, and unchanged.
- **Engine extraction**: PASS for all three engines' own page-2 text/cell content (every value physically printed on page 2 was read correctly by pdfjs-dist and pymupdf; Docling's own cell segmentation is where its new column-fusion defect lives).

- **Document/layout-family interpretation**: the dominant failure layer for this case — the single-page-scope architecture cannot recover cross-page item context, a limitation that was invisible in case-001/002/003 only because their target rows happened to share a page with their own item header.
